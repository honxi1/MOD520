第 5 章 · 打包与发布

功能做完不等于可以发出去。本章带你走完构建、测试、版本管理和发布流程，让 MOD 能稳定地交到玩家手里。

本章目录
  1. 构建产物
  2. 发布前测试清单
  3. 版本管理
  4. 发布到社区
  5. 常见问题

1. 构建产物

运行构建任务得到可分发的 jar 文件：

gradlew build

产物通常位于 build/libs/ 下，形如 mymod-1.0.0.jar。检查要点：

  • 用压缩工具打开 jar，确认元信息、资源、语言文件都在 src/main/resources 对应的路径。
  • 确认没有打包进调试用的临时文件。
  • 确认文件名与版本号对应，方便玩家识别。

2. 发布前测试清单

项目说明
干净环境启动只装你的 MOD 启动，验证无报错
长时间运行挂机 / 游玩数小时，观察内存与日志
服务端+客户端若涉及多人，单独测试服务端，检查同步
与其他 MOD 共存至少与常用的同类 MOD 一起测试
旧存档兼容用早期版本存档加载，确认不崩、数据不丢
永远不要在只测试了「自己开单机」后就发布。多人服、旧存档、MOD 共存是崩溃重灾区。

3. 版本管理

遵循语义化版本（主版本.次版本.修订号）：

  • 修复 Bug、不影响存档 → 修订号 +1（1.0.0 → 1.0.1）。
  • 新增功能、向后兼容 → 次版本 +1（1.0.0 → 1.1.0）。
  • 破坏性改动、不兼容旧存档 → 主版本 +1（1.0.0 → 2.0.0）。

每次发布都用 Git 打标签，方便回滚与追溯：

git tag -a v1.0.1 -m "release v1.0.1"
git push origin v1.0.1

4. 发布到社区

  1. 编写 README：功能简介、安装方法、已知问题、兼容版本、开源协议。
  2. 准备封面图与演示截图，写清「支持的游戏版本」和「依赖」。
  3. 发布到对应社区平台，一个发布条目包含：jar 文件、版本号、更新日志、下载链接。
  4. 发布后关注反馈，及时处理崩溃报告；遇到「带日志的崩溃报告」要感谢并优先回复。

5. 常见问题

  • 玩家说「装了没用」：大概率是放错目录或版本不匹配，README 里写清楚安装路径。
  • 崩溃报告满天飞：先复现，再修，不要为了快出补丁而掩盖根因。
  • 要不要开源：开源利于社区维护和口碑，但要在 README 里声明协议，防止他人误用。
到这里你已经走完了「搭环境 → 写 MOD → 配资源 → 做功能 → 发版本」的完整流程。接下来把教程里学到的东西做进一个真实项目里吧——欢迎把成果提交到本仓库。
