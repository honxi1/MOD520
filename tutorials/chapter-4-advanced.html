第 4 章 · 进阶功能

会注册内容之后，再来学真正让 MOD「活起来」的东西：事件系统、与其他 MOD 的互操作，以及一些常见的玩法逻辑。

本章目录
  1. 事件系统
  2. 挂接点与回调
  3. 与其他 MOD 互操作
  4. 常见玩法逻辑
  5. 常见问题

1. 事件系统

事件是游戏向你通知「发生了什么」的机制。不要靠轮询判断状态，用事件订阅更高效、更稳定：

events.register(PlayerJoinEvent.class, event -> {
    Player player = event.getPlayer();
    player.sendMessage("欢迎回来，" + player.getName() + "！");
});

常见事件：玩家加入/退出、实体受伤/死亡、方块被破坏/放置、物品被使用、世界生成等。写逻辑前先查一下有没有现成事件，不要重复造轮子。

2. 挂接点与回调

有些扩展点是「回调式」的：你把自己的函数传给框架，框架在合适时机调用它。例如自定义方块的行为：

registerBlock(new MyBlock(), block -> {
    block.onPlaced((world, pos, player) -> {
        // 放置时的逻辑
    });
    block.onBroken((world, pos, player) -> {
        // 被破坏时的逻辑
    });
});

回调里 不要做耗时操作（读写磁盘、网络请求），它们运行在主线程，会卡住游戏。耗时工作放异步线程，完成后切回主线程更新。

3. 与其他 MOD 互操作

  • 软依赖：你的 MOD 在有对方时增强功能，没有时也能正常运行。用「可选依赖 + 反射/服务接口」实现，不要直接强引用。
  • API 模块：把接口抽到独立 jar，其他 MOD 只依赖接口，避免双向耦合。
  • 版本兼容：通过能力探测（capability）判断对方版本，不要假设 API 不变。
强依赖其他 MOD 会让对方更新时你的 MOD 直接崩溃。优先用软依赖 + 能力探测。

4. 常见玩法逻辑

下面是一个「合成结果附带掉落」的典型组合示例——把一个合成事件和一个掉落事件组合出完整玩法：

events.register(CraftEvent.class, e -> buffedLevel(e));
events.register(EntityDeathEvent.class, e -> dropExtra(e));

编写玩法逻辑时的三条经验：

  • 数值一律走配置文件，方便平衡调整。
  • 服务端做判定，客户端只做表现，防止作弊与不同步。
  • 每个事件处理保持幂等，避免重复触发叠加效果。

5. 常见问题

  • 事件不触发：确认你订阅的事件类与注册时机正确（有些事件只发生在服务端）。
  • 游戏卡顿：检查是否在回调里做了耗时操作，或事件处理器数量过多。
  • 与某 MOD 冲突：先用「只装你 + 对方」复现，再决定是软依赖还是改注册时机。
练习：给上一章的物品加一个「手持时按住右键持续回复生命」的效果，用事件 + 配置文件控制每秒回复量。
